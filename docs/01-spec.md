## 2. 术语表

| 术语 | 含义 |
|---|---|
| **会话（Session）** | 一次面试的运行时状态：问题列表、当前进度、每题状态与作答。当前存于**后端进程内存** |
| **记录（Record）** | 一次已完成面试的持久化结果，含对话与报告，落在 `interview_records` |
| **报告（Report）** | AI 对一次面试的结构化评分，JSON，存 `interview_records.report` |
| **审核** | 管理员把记录状态改为 `approved`/`rejected` 并写评语 |
| **反问** | 候选人向 AI 面试官提问（如"能先让我自我介绍吗"） |
| **跳过词** | **23 个**关键词（`interview.py:27-29`、`App.tsx:589-591`，两侧集合已实测相同），命中即视为跳过当前题 |
| **REG（回归）** | 现状已可用，本轮只须保证不被破坏，**不投入新开发** |

**优先级定义（v2 修订）**
- **P0**：本轮必须实现或修复，否则不可发布（安全缺口 / 主流程阻塞 / 核心卖点失效）
- **P1**：本轮应完成
- **P2**：可选或延后
- **REG**：功能已存在、本轮**不新增功能**，只须保证不被破坏。**注**：标记 REG 的条目仍可能附带本轮必修的缺陷修复（如 FR-8.3 的事务化），此时以"REG + 该条自身的验收标准"为准，二者不矛盾。

**统计口径**：`范围外` 条目（FR-1.7）不计入 P0/P1/P2 分布。

## 4. 功能性需求

### FR-1 账号与认证

| ID | 需求 | 优先级 | 现状 | 验收标准 |
|---|---|---|---|---|
| FR-1.1 | 用户名+邮箱+密码+验证码注册 | P0 | ⚠️ | 用户名 3-16 位（中/英/数/下划线）且唯一，邮箱格式正确且唯一。**后端必须独立强制密码强度（8-16 位、≥2 类字符、无 6 位连续或重复），不得仅依赖前端**（当前 `auth_router.py:44-48` 只判空，可绕过） |
| FR-1.2 | 用户名+密码+验证码登录 | P0 | ✅ REG | 成功返回 JWT 与 role；失败统一提示"用户名或密码错误"。**令牌有效期须取自 `config.ACCESS_TOKEN_EXPIRE_MINUTES` 单一常量**（当前 `auth.py:114` 自带 15 分钟默认值且未使用已 import 的该常量，主路径靠 `auth_router.py:94-97` 显式传 30 分钟，属隐患）。**v2.2 补契约**：**30 分钟 + 滑动续期**，续期经响应头 **`X-Refreshed-Token`**（须加入 CORS `expose_headers`）；token 含 **`auth_time`**，**自首次签发起 8 小时为续期绝对上限**，超限返回 `401` + `X-Token-Expired: absolute`；前端须提示重新登录**且保留服务端面试进度** |
| FR-1.3 | 图形验证码与失败限流 | P0 | ⚠️ | 4 位数字，TTL 300 秒，一次性。限流语义须写明：**10 分钟滑动窗口内累计 5 次失败则拒绝**（验证码失败与密码失败共用同一计数桶，登录成功清空）。**存储须支持多进程**（ADR-004）；**客户端 IP 须从可信代理头解析**（ADR-015，否则反代下全员共用一个计数器） |
| FR-1.4 | 登出 | P1 | ❌ | 服务端可失效令牌。当前为纯前端清 localStorage，JWT 在有效期内仍可用（依赖 ADR-003 选 B） |
| FR-1.5 | 修改密码 | **P0** | ⚠️ | 需校验原密码；**新密码规则必须与注册规则完全相同（同一校验函数）**，不得出现"前端 ≥6 / 后端 ≥8"的冲突（`App.tsx:1173` vs `user.py:100`）。成功后要求重新登录；"强制失效"依赖 FR-1.4，若 FR-1.4 未做则仅前端登出 |
| FR-1.6 | 管理员重置用户密码 | P1 | ✅ REG | 新密码 ≥8 位；**仅 admin 可调用**（`get_current_admin_user`）；用户不存在返回 404。**本轮裁决：允许重置任意用户（含 admin 账号）**——当前仅单管理员且无其他恢复途径，禁止将导致管理后台无法恢复；实现方不得自行加禁用逻辑 |
| FR-1.7 | 密码找回 / 邮箱验证 | 范围外 | ❌ | **本轮范围外**（依赖邮件服务，见 A-10、§7）。**不建立阶段 5 任务** |
| FR-1.8 | 挂载时校验登录态 | P1 | ⚠️ | 应用挂载时用已存令牌探测一次；401 则清理本地状态并回到未登录态（当前逻辑存在但未纳入需求） |
| FR-1.9 | 用户协议可访问 | P2 | ❌ | 注册页《用户协议》当前为 `href="#"` 死链，须指向真实页面或移除勾选项 |

### FR-5 评估报告

## 9. 验收原则

1. **P0 需求全部通过**方可进入阶段 9 集成测试；任一 P0 不通过则不得发布。
2. **每个 P0/P1 需求至少有一条可执行测试**（阶段 6 产出测试计划）。**NFR-6 为 P0 即由此派生**——无测试基建则 P0 无法验证。
3. **回归保护**：标记 `REG` 的已实现功能，改造后必须仍然通过（重点：FR-2.5 越权防护、FR-7.2 去重窗口、FR-7.5 轮询间隔、FR-8.4 详情渲染、**FR-8.6 删除记录**、**FR-4.2(b) 无会话时的明确报错**）。
4. 任何对**需求或架构**的变更，必须回到本文件更新编号，**不得在编码阶段直接改需求**。
5. **接口契约变更**（如 FR-2.4 取消 `/api/chat` 的 `user_id`、FR-5.2 失败响应形状）必须同步更新本文件的验收标准与前端适配。
