## 2. Bug 详情

### Bug 1 · 核心接口"裸奔" 🔴

| 项 | 内容 |
|---|---|
| **现象** | `POST /api/chat` 与 `POST /api/resume/upload` **完全没有鉴权**（未挂 `Depends`）；且 `/api/chat` 的 `user_id` **由客户端请求体提供**，可任意伪造 |
| **业务场景** | 任何人无需登录，用 Postman 等工具直接发 HTTP 请求 |
| **用户操作** | 未登录用户发请求；或攻击者伪造他人 `user_id` 发请求 |
| **预期结果** | 必须携带有效 Token 才能访问，且只能操作**自己的**面试会话 |
| **实际异常** | 未登录/Token 失效被放行；**白嫖 DeepSeek API 额度**；**读写、推进他人的内存面试会话（串号）** |
| **根因** | 路由签名缺鉴权依赖（`interview.py:33-34`、`:279-280`）；会话以客户端提供的 id 为键（`:39-40`） |
| **影响面** | 安全 + 成本 + 数据完整性；**同时是 DoS 与越权入口** |
| **代码位置** | `backend/routers/interview.py:33`、`:39-40`、`:279` |
| **与 spec 映射** | **FR-2.4（P0）** + **NFR-1(a)** |
| **处置** | ✅ 已被覆盖，**无需新增需求**。外部反馈新增的唯一约束是**上线顺序**，已写入 FR-2.4 验收 |

**反馈给出的解法（与既有裁决一致）**：
1. 强制挂载 `require_user` / `get_current_user` 依赖；
2. 废弃请求体 `user_id`，统一从 JWT 解析 `current_user.id`；
3. **上线顺序：必须与"会话持久化（Bug 2）"同批上线**，否则前端首条消息会因无 `user_id` 报 409。

> **注**：第 3 条正是 `01-spec.md` v2.1 就 N2 作出的裁决，架构 §4.2 已重申为**发布门禁**。外部反馈独立复现了同一结论 —— 这是对该裁决的有力交叉验证，**不改**。

### Bug 2 · 刷新页面即报废 🔴

| 项 | 内容 |
|---|---|
| **现象** | `user_id` 只存于前端内存（`App.tsx` 的 State），未持久化；而 `/api/chat` 恰好靠它取会话 |
| **业务场景** | 用户答题中按 F5 刷新，或关掉浏览器重新打开 |
| **用户操作** | 点击刷新按钮，或重新打开页面 |
| **预期结果** | 页面**恢复当前面试进度**，可继续作答 |
| **实际异常** | 内存清空 → `user_id` 为 `null` → 后端查不到会话 → 走无会话的角色扮演分支；**进度圆点、跳过状态全部失效** |
| **根因** | 前端未持久化 `userId`（`App.tsx:472,945`）；**后端无任何接口可取回会话状态**；会话存进程内存 |
| **影响面** | 主流程可用性；**用户在面试中途丢失全部进度** |
| **代码位置** | `frontend/src/App.tsx:472`、`:945`、`:602`；`backend/routers/interview.py:39-40`、`:19` |
| **与 spec 映射** | **FR-4.4（P0）** + FR-4.11 + **NFR-5（P0）** |
| **处置** | ✅ 已被覆盖，**无需新增需求** |

**反馈给出的解法（与 ADR-004/ADR-022 一致）**：
1. 前端把 `token` **和 `userId`** 持久化到 `localStorage`；
2. 后端新增 **`GET /api/interview/session`**，前端挂载时主动拉取并重建视图；
3. 后端**用数据库表存储会话**，不再依赖进程内存（支持多进程部署）。

> **注**：架构 ADR-004 已推荐"落 SQLite 表"（选项 B），ADR-022 已定义 `GET /api/interview/session` 与恢复/放弃交互；v2.1 终审进一步指出"**仅持久化 `userId` 不足以修复**——必须配合会话读取接口"，同时补上"冲突返回 409 且携带会话摘要"。反馈第 1 条与第 2 条**必须成对实施**，与架构结论一致。

### Bug 3 · 15 分钟超时闭环断裂 🔴 ⭐（本次反馈的重点）

外部反馈把本 Bug **明确拆成两个独立子问题**——**这正是既有规格的覆盖缺口所在**：

#### 3A · 超时闭包失效（报告生成不出来）

| 项 | 内容 |
|---|---|
| **现象** | 定时器闭包捕获旧渲染数据（`messages = []`） |
| **预期** | 强制结束面试，生成报告 |
| **实际异常** | 提示**无法生成报告**（因为捕获了空的 `messages`） |
| **根因** | 倒计时回调与 `setTimeout` 捕获创建时渲染的 `messages`；且**报告只依赖前端传入的消息** |
| **与 spec 映射** | ✅ **FR-4.5（P0）** 已覆盖 |
| **处置** | 无需新增 |

#### 3B · 状态未强制重置（UI 不销毁，可继续答题）❌ **既有规格未覆盖**

| 项 | 内容 |
|---|---|
| **现象** | 超时后**未强制重置前端状态** |
| **业务场景** | 用户开启面试后，15 分钟不作答 |
| **用户操作** | 无操作，等待倒计时归零 |
| **预期结果** | **强制结束面试，生成报告，并锁定 UI** |
| **实际异常** | **UI 没有销毁，用户依然可以继续答题**，完全违背 15 分钟倒计时的业务逻辑 |
| **根因** | 前端超时分支未重置 `interviewStarted` / 未销毁输入区（`App.tsx:781-791` 只调用了 `endInterview`，其失败路径直接 `return`，残留状态无人清理） |
| **影响面** | **业务规则失效**（15 分钟限制形同虚设）；用户可无限作答 |
| **与 spec 映射** | ❌ **未覆盖** —— FR-4.5 只规定"必须出报告"，**未规定"必须打断主流程并锁定 UI"** |
| **处置** | 🆕 **新增 FR-4.12（P0）** |

> **命名对齐提示**：反馈中的 `isInterviewing` 对应代码实际的 `interviewStarted`（`App.tsx:457`）；结束态为 `interviewFinished`（`:461`）。

**反馈给出的解法（关键：服务端也必须兜底）**：
1. 用 `useRef` 存储**最新**消息列表与结束回调，避免闭包过期；
2. 报告数据**以后端服务端会话为准**，不再依赖前端传入的消息；
3. 超时逻辑**强制重置状态**（清空面试中状态），页面跳转/弹窗遮罩，**销毁输入框**；
4. **强制闭环：无论报告是否生成成功，超时后必须立刻打断主流程，并给用户明确反馈。**

> **⚠️ 架构补充要求（本文新增）**：仅靠前端锁定是**可绕过的**（用户仍可手工 `POST /api/chat`）。因此 FR-4.12 必须**同时**在服务端落实 —— 架构 ADR-004 已为 UPDATE 加上 `AND status='active' AND expires_at > :now` 条件，超时后服务端须将会话置为 `finished`/`abandoned`，使后续写入返回 409。**前端锁定 + 服务端拒绝，缺一不可。**

### Bug 4 · 环境差异导致按钮失灵 🟠

| 项 | 内容 |
|---|---|
| **现象** | 前端硬编码 `http://127.0.0.1:8000`，未配置 Vite Proxy |
| **业务场景** | 本地终端启动运行正常，但在 **Agent 预览环境 / 线上 HTTPS 环境**下运行 |
| **用户操作** | 点击"重置密码"等**任何**需要发请求的按钮 |
| **预期结果** | 成功弹出重置密码框，或请求成功 |
| **实际异常** | **点击无反应**（混合内容拦截或跨域被静默阻断） |
| **根因** | `frontend/src/config.ts:1` 默认绝对地址；`vite.config.ts` 全文仅 7 行、**无 `server.proxy`**；后端 CORS 仅放行 `localhost:5173/5174` |
| **影响面** | **生产环境整体不可用**（HTTPS 页面请求 HTTP 绝对地址 → 混合内容被浏览器直接阻断） |
| **代码位置** | `frontend/src/config.ts:1`、`frontend/vite.config.ts`、`backend/main.py:20` |
| **与 spec 映射** | **NFR-10(b)** 已覆盖，但优先级为 **P1**，**与其"使应用整体不可用"的实际影响不匹配** |
| **处置** | ⬆️ **NFR-10 由 P1 提升为 P0** |

**反馈给出的解法（与 ADR-005/ADR-011 一致）**：
1. 前端改为**相对路径**（`/api/...`）；
2. `vite.config.ts` 配置 `server.proxy` 代理到后端；
3. 用环境变量 `VITE_API_BASE_URL` 注入后端地址，彻底告别绝对地址硬编码。

> **提级理由**：本地开发"看起来正常"是**假象**——该问题一旦进入预览/HTTPS 环境即导致**所有按钮失效**，属"应用整体不可用"级缺陷；且它是阶段 10 部署的前置条件。按 `01-spec.md` 自定的 P0 判据（"主流程阻塞"），应列 P0。

### Bug 5 · 数据库与代码健康度 🟡（4 个子项）

| 子项 | 现象 | 与 spec 映射 | 处置 |
|---|---|---|---|
| **5-a** 迁移失控 | 无 Alembic，手写 `ALTER TABLE` 加出**死列** `notifications.link_url` | ADR-009、**FR-11.1（P2）** | ✅ 已覆盖 |
| **5-b** 死依赖/死代码 | `react-router-dom` 未使用；`QuestionBank.tsx` 无人引用；`services/api.ts` 大量零调用 | **FR-11.1（P2）**、ADR-005 | ✅ 已覆盖（本轮将启用前两者） |
| **5-c** 硬编码风险 | 管理员密码 `admin123`；简历生成的 7 个问题写死 | **NFR-1(d)**、ADR-017、**FR-3.4（P0）** | ✅ 已覆盖 |
| **5-d** 静默失败 | 前端 `catch` 里没有提示，**用户无感知** | **FR-6.2（P0）** 仅覆盖 `save_interview` | ⚠️ **覆盖过窄** → 🆕 **新增 NFR-13（P1）** |

| 项 | 内容（对应"场景拆解"） |
|---|---|
| **业务场景** | 后续迭代增加新字段、排查线上问题、用户体验操作失败 |
| **用户操作** | 修改表结构、点击操作、上传简历 |
| **预期结果** | 版本化迁移、干净重构、**错误有明确提示**、AI 真实解析简历 |
| **实际异常** | 改表结构导致线上事故；代码臃肿难维护；**用户以为已保存（其实落库失败）**；**简历跟问题毫无关系** |

**反馈给出的解法**：
1. 引入 Alembic，移除 `create_all()` 与手写 `ALTER`；
2. 清理死代码/死依赖，**启用 `react-router-dom` 路由**；
3. 密码改用**环境变量注入**；简历**启用 `RESUME_QUESTION_MODE=ai`** 真实解析；
4. **在 `catch` 块统一加 `alert(error.message)` 或统一错误组件，拒绝静默失败**。

> **⚠️ 关于第 4 条**：既有 **FR-6.2** 只要求"报告落库失败必须可见"，而反馈要求的是**全局**拒绝静默失败（所有 `catch`）。范围不同 → 新增 **NFR-13** 承接，FR-6.2 保持聚焦。
> **⚠️ 关于第 4 条的实现提醒**：`alert()` 是阻断式交互且不可测试，建议采用**统一错误组件 + Toast**（与架构 ADR-025 的 `ErrorBoundary`、§9 的统一错误提示一致），并在验收标准中要求"可被自动化测试断言"。

## 5. 关键结论与需确认事项

### 5.1 结论

1. **外部反馈与既有规格高度收敛**，无冲突。5 个 Bug 中 4 个已被既有 P0 需求覆盖，说明阶段 0-4 的逆向盘点与规格化工作是有效的。
2. **真正的增量只有 3 项**：新增 FR-4.12（超时强制闭环）、新增 NFR-13（全局拒绝静默失败）、NFR-10 提级。
